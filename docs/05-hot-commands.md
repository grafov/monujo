# 05. Команды `hot`

Группа `hot` управляет локальным зашифрованным **горячим кошельком**:
создаёт и импортирует ключи, показывает локальный список, активирует
аккаунты, отправляет TRX и USDT.

```text
monujo hot
├── list          — показать локальные кошельки
├── create        — создать новый кошелёк (случайный ключ)
├── import        — импортировать существующий ключ (hex)
├── activate      — отправить TRX на новый адрес, чтобы он появился on-chain
├── balance       — баланс TRX и USDT для именованного кошелька
├── send-trx      — отправить TRX
└── send-usdt     — отправить USDT (TRC-20)
```

Глобальные ключи (`--network`, `--output`, `--api-key`,
`--keystore-dir`, `--http-url`, `--grpc-url`) применимы ко всем
подкомандам. Подробнее см. [03 — Конфигурация](03-configuration.md).

## Общие принципы

- **Ввод парольной фразы**. Любая команда, которой нужен приватный
  ключ (всё, кроме `list` и просмотра справки), запрашивает парольную
  фразу через TTY без эха. При создании/импорте — два раза подряд для
  подтверждения. Если STDIN не TTY (например, при запуске из скрипта),
  программа всё равно прочитает строку, но без скрытия ввода.
- **Стирание секретов**. Парольная фраза и материал приватного ключа
  затираются нулями (`ZeroPassphrase`, `Wipe`) сразу после
  использования.
- **Подтверждение сети**. Если файл кошелька уже содержит
  непустой список `networks` и текущий `--network` в нём
  отсутствует, перед запросом пароля выводится предупреждение и
  запрашивается подтверждение `[y/N]`. Чтобы пропустить это
  подтверждение в скриптах — `--force`. Без TTY и без `--force`
  возвращается ошибка `network mismatch: use --force to proceed
  without a terminal, or run interactively to confirm`.
- **Запись метаданных**. После успешной отправки TRX или USDT
  программа дописывает текущий `--network` в массив `networks`
  файла кошелька (без перешифрования; меняются только метаданные,
  атомарной заменой через `rename`).
- **Имя кошелька** (`--name`) санитизируется: разрешены только
  `a-z`, `A-Z`, `0-9`, `-` и `_`. Прочие символы заменяются на `_`.
  Пустое имя превращается в `default` (так что `--name " "` создаст
  файл `default.json`).

## `hot list`

Показывает локально сохранённые кошельки: имя, адрес, перечень сетей
из метаданных. **Расшифровывание не выполняется**, парольная фраза
не нужна.

### Использование

```bash
monujo hot list
monujo --output json hot list
```

### Флаги

Локальных флагов нет. Локально считывается каталог
`--keystore-dir`/`MONUJO_KEYSTORE_DIR`/`~/.config/monujo/keystore`.

### Что происходит

1. Открывается каталог keystore. Если его нет, выводится пустой
   список (без ошибки).
2. Перебираются все `*.json` (подкаталоги пропускаются).
3. Каждый файл парсится как `EncryptedWalletFile`. Файлы с другой
   версией формата или без поля `address` тихо пропускаются.
4. Записи сортируются по имени.

### Пример: формат `table`

```text
$ monujo hot list
Keystore: /home/user/.config/monujo/keystore
NAME    ADDRESS               NETWORKS
funding TFG7NgT...            mainnet,shasta
imported TXYZ...              -
myhot   TLcVUPa...            shasta
```

Колонки разделены табуляцией. Если в `networks` пусто — печатается `-`.
Если каталог пуст — `No wallets.`.

### Пример: формат `json`

```json
{
  "keystore_dir": "/home/user/.config/monujo/keystore",
  "wallets": [
    {"name": "funding", "address": "TFG7NgT...", "networks": ["mainnet", "shasta"]},
    {"name": "imported", "address": "TXYZ..."},
    {"name": "myhot", "address": "TLcVUPa...", "networks": ["shasta"]}
  ]
}
```

`networks` пропускается из JSON, если пусто (тег `omitempty`).

## `hot create`

Создаёт **новый** кошелёк: генерирует случайный secp256k1 ключ,
выводит из парольной фразы scrypt‑ключ, шифрует приватный ключ
AES‑256‑GCM, записывает файл с правами `0600`. Текущий `--network`
автоматически попадает в метаданные `networks` нового файла.

### Использование

```bash
monujo hot create --name <ИМЯ> [--export-private-key]
monujo --network shasta hot create --name testhot
monujo --output json hot create --name myhot --export-private-key
```

### Флаги

| Флаг | Тип | Обязательный | По умолчанию | Описание |
|------|-----|--------------|--------------|----------|
| `--name` | string | да | — | Имя кошелька. Превратится в файл `<safeName>.json` в `--keystore-dir`. |
| `--export-private-key` | bool | нет | `false` | Печатать сгенерированный приватный ключ один раз. **Опасно**: ключ окажется в выводе терминала или JSON‑потоке. |
| `--overwrite` | bool | нет | `false` | **ОПАСНО**: разрешить замену уже существующего файла кошелька. Старый приватный ключ будет безвозвратно потерян. На TTY дополнительно запрашивается `[y/N]`; без TTY выполняется без доп. подтверждения. |

### Что происходит

1. Запрашивается новая парольная фраза дважды. При несовпадении —
   ошибка `passphrases do not match`.
2. Генерация ключа: `crypto.GenerateKey()` из go‑ethereum.
3. Из публичного ключа вычисляется Tron‑адрес.
4. Шифрование: `scrypt(passphrase, random_salt, N=32768, r=8, p=1, 32)` →
   `AES-256-GCM(nonce=random_12, plaintext=raw_priv_32)`.
5. Файл `<keystore_dir>/<safeName>.json` создаётся с правами `0600`.
   Если каталога ещё нет, он создаётся с правами `0700`.

### Пример: формат `table`

```text
$ monujo hot create --name myhot
New keystore passphrase: ********
Confirm passphrase: ********
Created wallet "myhot" -> TLcVUPa...
Keystore: /home/user/.config/monujo/keystore
```

С `--export-private-key`:

```text
$ monujo hot create --name myhot --export-private-key
...
WARNING: printing private key is unsafe; anyone with this hex can spend funds.
Private key (hex): 7b8a...c9d0
```

### Пример: формат `json`

```json
{
  "name": "myhot",
  "address": "TLcVUPa...",
  "path": "/home/user/.config/monujo/keystore"
}
```

С `--export-private-key`:

```json
{
  "name": "myhot",
  "address": "TLcVUPa...",
  "path": "/home/user/.config/monujo/keystore",
  "private_key_hex": "7b8a...c9d0"
}
```

### Что важно знать

- Адрес, полученный из ключа, действителен в **обеих** сетях
  (mainnet и Shasta). Метка `--network` влияет только на то, какая
  сеть запишется в `networks` метаданных и какая будет использоваться
  по умолчанию для последующих команд.
- Файл создаётся через прямой `os.WriteFile` (не атомарно). Если
  процесс прерван между генерацией ключа и записью файла, ключ
  будет потерян, поскольку приватный ключ только что генерировался
  в памяти и не сохраняется нигде.
- Если файл с таким именем **уже существует**, команда по умолчанию
  завершается с ошибкой `wallet "<имя>" already exists at <путь>;
  use --overwrite to replace (DANGEROUS, irreversible)` ещё до
  запроса парольной фразы. Замена возможна только с явным
  `--overwrite`: на TTY дополнительно запрашивается `[y/N]`, в
  неинтерактивном режиме (скрипт, CI, перенаправленный stdin)
  перезапись выполняется без доп. подтверждения — сам флаг считается
  подтверждением. Потерянный таким образом приватный ключ **не
  восстановим**.

## `hot import`

Импортирует существующий приватный ключ (64 hex‑символа) в новый файл
keystore. Текущий `--network` записывается в метаданные.

### Использование

```bash
monujo hot import --name <ИМЯ> --key-hex <64_HEX>
# или
MONUJO_IMPORT_KEY=<64_HEX> monujo hot import --name <ИМЯ>
monujo --network shasta hot import --name testhot --key-hex 0x...
```

### Флаги

| Флаг          | Тип    | Обязательный | По умолчанию | Описание                                                                                                                                                           |
|---------------|--------|--------------|--------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `--name`      | string | да           | —            | Имя файла keystore.                                                                                                                                                |
| `--key-hex`   | string | нет          | —            | 64 hex‑символа приватного ключа secp256k1. Опционально с префиксом `0x`.                                                                                           |
| `--overwrite` | bool   | нет          | `false`      | **ОПАСНО**: разрешить замену уже существующего файла кошелька. Старый приватный ключ будет безвозвратно потерян. На TTY — с подтверждением `[y/N]`; без TTY — без. |

Если `--key-hex` не задан, программа берёт ключ из переменной
`MONUJO_IMPORT_KEY`. При отсутствии и того, и другого — ошибка:

```
provide --key-hex or set MONUJO_IMPORT_KEY with the hex private key
```

### Что происходит

1. Парсится hex‑ключ: проверяется длина (ровно 64 символа) и
   корректность (валидный ECDSA secp256k1, не все нули).
2. Если файл с таким именем уже есть в keystore, команда
   отказывается продолжать без `--overwrite` (аналогично
   `hot create`, см. соответствующий раздел выше).
3. Запрашивается пароль дважды.
4. Шифруется и сохраняется так же, как в `hot create`.
5. Адрес в файле — детерминированно из ключа.

### Пример: формат `table`

```text
$ monujo hot import --name imported --key-hex 7b8a...c9d0
New keystore passphrase: ********
Confirm passphrase: ********
Imported wallet "imported" -> TXYZ...
Keystore: /home/user/.config/monujo/keystore
```

### Пример: формат `json`

```json
{
  "name": "imported",
  "address": "TXYZ...",
  "path": "/home/user/.config/monujo/keystore"
}
```

### Безопасность

- Ключ из переменной окружения может попасть в логи и историю
  shell. Используйте `MONUJO_IMPORT_KEY` только в контролируемом
  окружении (одноразовая запись, без записи в `.bash_history`).
- В режиме `table` сам ключ нигде не печатается; в режиме `json`
  тоже — `import` не имеет аналога `--export-private-key`.

## `hot activate`

«Активирует» новый адрес в TRON, переводя ему небольшую сумму TRX с
уже фондированного кошелька. Это просто синоним
`hot send-trx`, но с понятной семантикой и обязательным указанием
`--from`/`--to`/`--amount`.

> Историческая справка: в TRON аккаунт «появляется» в реестре после
> первой входящей транзакции. Без активации watch‑запросы по новому
> адресу будут возвращать пустые данные.

### Использование

```bash
monujo --network shasta hot activate \
       --from funding --to <NEW_ADDR> --amount 1
```

### Флаги

| Флаг       | Тип    | Обязательный | По умолчанию | Описание                                                                                       |
|------------|--------|--------------|--------------|------------------------------------------------------------------------------------------------|
| `--from`   | string | да           | —            | Имя кошелька, с которого спишутся TRX. Должен иметь TRX в выбранной сети.                      |
| `--to`     | string | да           | —            | Tron‑адрес получателя (Base58).                                                                |
| `--amount` | string | да           | —            | Сумма TRX (десятичное число, до 6 знаков после запятой).                                       |
| `--force`  | bool   | нет          | `false`      | Не запрашивать подтверждение, если `--network` отсутствует в `networks` фондирующего кошелька. |

### Что происходит

То же, что и `hot send-trx --name <from>`: проверка адреса, запрос
пароля, расшифровывание, построение транзакции через gRPC,
подписание ECDSA, broadcast, дозапись `--network` в метаданные
кошелька‑источника.

Альтернатива на Shasta: использовать
[Shasta‑faucet](https://www.trongrid.io/faucet) — бесплатный
крадиновый сервис, активирующий адрес без оплаты.

## `hot balance`

Показывает баланс TRX и USDT для **именованного** локального
кошелька. Адрес берётся из расшифрованного keystore (фактически тот
же запрос, что у `watch balance`, но без необходимости вспоминать
адрес).

### Использование

```bash
monujo hot balance --name <ИМЯ>
monujo --network shasta hot balance --name testhot --force
```

### Флаги

| Флаг      | Тип    | Обязательный | По умолчанию | Описание                                                                                        |
|-----------|--------|--------------|--------------|-------------------------------------------------------------------------------------------------|
| `--name`  | string | да           | —            | Имя кошелька в keystore.                                                                        |
| `--force` | bool   | нет          | `false`      | Пропустить интерактивное подтверждение, если текущий `--network` не записан в `networks` файла. |

### Что происходит

1. Проверка `networks` файла → возможное подтверждение.
2. Запрос пароля.
3. Расшифровка keystore (`LoadPrivateKey`).
4. Извлечение адреса (`PrivKey.Address`).
5. Тот же HTTP‑запрос, что в `watch balance`, и тот же формат
   вывода (`table`/`json`).

Расшифрованный приватный ключ сразу же стирается; balance‑запрос его не
использует, но дешифрование нужно для проверки целостности файла
(в `LoadPrivateKey` сверяется, что выведенный адрес совпадает с тем,
что записан в `EncryptedWalletFile.Address`).

### Пример

```text
$ monujo hot balance --name myhot
Passphrase: ********
Address: TLcVUPa...
TRX:     50.123456 (50123456 sun)
USDT:    100 (minimal units 100000000)
```

В JSON структура такая же, как у `watch balance` (см. [04](04-watch-commands.md#пример-формат-json)).

## `hot send-trx`

Отправляет нативный TRX с локального кошелька на любой адрес.

### Использование

```bash
monujo hot send-trx --name <ИМЯ> --to <ADDR> --amount <TRX>
```

### Флаги

| Флаг       | Тип    | Обязательный | По умолчанию | Описание                                     |
|------------|--------|--------------|--------------|----------------------------------------------|
| `--name`   | string | да           | —            | Имя кошелька‑источника.                      |
| `--to`     | string | да           | —            | Tron‑адрес получателя.                       |
| `--amount` | string | да           | —            | Сумма TRX (десятичное число, до 6 знаков).   |
| `--force`  | bool   | нет          | `false`      | Пропустить интерактивное подтверждение сети. |

### Что происходит

1. Подтверждение сети (см. общие принципы выше).
2. Запрос пароля.
3. Парсинг суммы: `domain.ParseTRXDecimal`. Допускается до 6 знаков
   после точки. Отрицательные числа, пустая строка, лишние символы
   и переполнение `int64` приводят к ошибке.
4. Валидация адреса получателя.
5. Расшифровка keystore.
6. Подключение по gRPC, построение транзакции
   (`gotron-sdk` `Transfer`), подписание ECDSA, рассылка
   (`Broadcast`).
7. Если broadcast вернул не‑нулевой код — ошибка `broadcast: <message>`.
8. Дозапись `--network` в метаданные.

### Пример: формат `table`

```text
$ monujo hot send-trx --name myhot --to TXYZ... --amount 12.5
Passphrase: ********
Broadcast OK
Network: mainnet
TxID:    abc123...
From:    TLcVUPa...
To:      TXYZ...
TRX: 12.5
```

### Пример: формат `json`

```json
{
  "tx_id": "abc123...",
  "from": "TLcVUPa...",
  "to": "TXYZ...",
  "kind": "TRX",
  "amount": "12.5",
  "network": "mainnet"
}
```

### Особенности

- Идентификатор транзакции вычисляется локально как
  `sha256(proto.Marshal(tx.GetRawData()))` — Tron использует именно
  этот хеш как `txID`. Поэтому `tx_id` доступен сразу после успешной
  рассылки, даже до её попадания в блок.
- Tron берёт оплату либо за счёт **bandwidth** (бесплатно, в пределах
  суточного лимита), либо «сжигая» TRX, если bandwidth исчерпан.
  monujo не запрашивает явной оценки fee; для нативных переводов это
  обычно безопасно. Если у адреса нет TRX вообще, broadcast
  завершится ошибкой.
- При успехе текущий `--network` будет добавлен в метаданные файла
  (если ещё не записан). Если файл по какой‑то причине не удалось
  обновить, программа всё равно сообщит об успешном broadcast и
  выведет ошибку метаданных:

  ```
  broadcast ok (tx <id>) but could not update wallet networks metadata: <причина>
  ```

## `hot send-usdt`

Отправляет USDT (TRC‑20) с локального кошелька на любой адрес.
Используется контракт, выбранный по `--network`:

- mainnet: `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t` (Tether),
- Shasta: `TG3XXyExBkPp9nzdajDZsozEu4BkaSJozs` (тестовый токен,
  **не настоящий** USDT).

### Использование

```bash
monujo hot send-usdt --name <ИМЯ> --to <ADDR> --amount <USDT>
```

### Флаги

| Флаг       | Тип    | Обязательный | По умолчанию | Описание                                                               |
|------------|--------|--------------|--------------|------------------------------------------------------------------------|
| `--name`   | string | да           | —            | Имя кошелька‑источника.                                                |
| `--to`     | string | да           | —            | Tron‑адрес получателя.                                                 |
| `--amount` | string | да           | —            | Сумма USDT (десятичное число, до 6 знаков). Должна быть положительной. |
| `--force`  | bool   | нет          | `false`      | Пропустить интерактивное подтверждение сети.                           |

### Что происходит

1. Подтверждение сети.
2. Запрос пароля.
3. Парсинг суммы: `domain.ParseUSDTDecimal` → `*big.Int` минимальных
   единиц. До 6 знаков после точки. Сумма должна быть строго
   положительной (`amount must be positive` иначе).
4. Валидация адреса получателя.
5. Расшифровка keystore.
6. gRPC: `TRC20Send(from, to, contract, amount, feeLimit=100_000_000 sun)` —
   формирует contract call USDT `transfer(address,uint256)`.
7. Подписание ECDSA, broadcast.
8. Дозапись `--network` в метаданные.

### Пример: формат `table`

```text
$ monujo hot send-usdt --name myhot --to TXYZ... --amount 10.25
Passphrase: ********
Broadcast OK
Network: mainnet
TxID:    def456...
From:    TLcVUPa...
To:      TXYZ...
USDT: 10.25 USDT
```

### Пример: формат `json`

```json
{
  "tx_id": "def456...",
  "from": "TLcVUPa...",
  "to": "TXYZ...",
  "kind": "USDT",
  "amount": "10.25 USDT",
  "network": "mainnet"
}
```

### Особенности

- TRC‑20 переводы тратят **energy**. Если у адреса не хватает
  стейкнутой `energy`, недостающее количество компенсируется
  сжиганием TRX, но не более `feeLimit = 100 TRX`. Если ваш баланс
  TRX меньше нужного, broadcast завершится ошибкой `OUT_OF_ENERGY`
  или `OUT_OF_TIME` от узла.
- Лимит комиссии (`100 TRX`) вшит в код (`config.defaultFeeLimitSun`).
  В текущей версии его нельзя поменять флагом.
- На Shasta тестовый USDT‑контракт может отличаться по поведению от
  настоящего Tether (decimals, события, методы — программа исходит
  из стандарта `transfer(address,uint256)` и 6 знаков). Перед
  использованием на Shasta убедитесь, что это именно тот контракт,
  для которого валиден этот вызов.

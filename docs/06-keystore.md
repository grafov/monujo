# 06. Хранилище ключей (keystore)

`monujo` хранит приватные ключи в локальном **зашифрованном
хранилище**. Каждый кошелёк — это отдельный JSON‑файл в каталоге,
заданном `--keystore-dir` / `MONUJO_KEYSTORE_DIR` / по умолчанию
`~/.config/monujo/keystore`.

## Расположение и права

- Каталог keystore создаётся автоматически (`os.MkdirAll(... 0o700)`)
  при первой записи (`wallet create`/`wallet import`).
- Файлы создаются с правами `0600` (`os.WriteFile(... 0o600)`).
- Имя файла строится из `--name` через функцию `safeName`:
  - разрешённые символы: `a-z A-Z 0-9 _ -`,
  - все прочие заменяются на `_`,
  - пустое имя превращается в `default`.
  Например, `--name "My Cold #1"` создаст файл `My_Cold__1.json`.
- При записи метаданных (см. ниже) используется атомарная замена через
  временный файл `.monujo-keystore-*.tmp` и `os.Rename`.
- Чтение ключа идёт через `os.OpenRoot(keystoreDir)`: открыть файл
  можно **только** внутри указанного каталога; попытка эскейпа через
  симлинк или `..` гарантированно провалится на уровне системного
  вызова, даже если в `safeName` появится дыра.

## Формат файла v2 (актуальный)

Текущая версия формата — `2` с KDF `argon2id`. Программа также читает
файлы версии `1` (legacy, scrypt) и при первой успешной разблокировке
**автоматически пересобирает их в v2** (см. раздел «Миграция v1 → v2»
ниже). Версии за пределами `{1, 2}` дают ошибку
`unsupported keystore version <N>`.

Пример минимального v2-файла:

```json
{
  "version": 2,
  "address": "TLcVUPaYnQp...",
  "networks": ["mainnet"],
  "kdf": "argon2id",
  "salt_hex": "8a7b...e1f2",
  "argon2_time": 3,
  "argon2_memory": 65536,
  "argon2_threads": 4,
  "argon2_key_len": 32,
  "cipher": "aes-256-gcm",
  "nonce_hex": "5c1d...90ab",
  "data_hex": "fa12...34cd"
}
```

### Внешняя запись (только адрес, без ключа)

Файл с `"external": true` хранит **именованный** Tron-адрес без KDF и без
шифротекста ключа. Его создаёт `monujo wallet import-external`. Минимальный
вид:

```json
{
  "version": 2,
  "external": true,
  "address": "TXmVpin5vq5gdZsciyyjdZgKRUju4st1wM",
  "networks": ["mainnet"]
}
```

Такие файлы участвуют в `wallet list` и в резолве имён в командах, где
нужен только адрес; `LoadPrivateKey`, `wallet check`, отправка с
`--from`, `offline sign` и `multisig cosign` для них **недоступны**.
Запись `networks` для внешнего файла задаётся при импорте и **не**
дополняется автоматически после транзакций (`EnsureNetworkRecorded` для
внешних записей запрещён).

### Поля v2

| Поле              | Тип             | Описание                                                                                                                                           |
|-------------------|-----------------|----------------------------------------------------------------------------------------------------------------------------------------------------|
| `version`         | int             | Всегда `2`.                                                                                                                                        |
| `address`         | string          | Tron‑адрес в Base58Check. Сверяется при дешифровании (если расшифрованный ключ даёт другой адрес — ошибка `address mismatch in keystore`).         |
| `networks`        | array of string | Опционально. Сети, на которых кошелёк уже использовался. Уникальные, отсортированные. `omitempty`.                                                 |
| `kdf`             | string          | Всегда `"argon2id"` для v2.                                                                                                                        |
| `salt_hex`        | string          | Случайная соль, 16 байт (128 бит) в hex. Требование NIST SP 800-132 §5.1.                                                                          |
| `argon2_time`     | uint32          | Параметр `t` (passes) argon2id. По умолчанию `3`.                                                                                                  |
| `argon2_memory`   | uint32          | Параметр `m` (memory cost) argon2id в KiB. По умолчанию `65536` = 64 MiB.                                                                          |
| `argon2_threads`  | uint8           | Параметр `p` (parallelism). По умолчанию `4`.                                                                                                      |
| `argon2_key_len`  | uint32          | Длина выводимого ключа в байтах. Всегда `32` (для AES-256).                                                                                        |
| `cipher`          | string          | Имя шифра: `"aes-256-gcm"`.                                                                                                                        |
| `nonce_hex`       | string          | Случайный nonce GCM, 12 байт в hex.                                                                                                                |
| `data_hex`        | string          | Шифротекст приватного ключа (32 байта плэйнтекста + 16 байт GCM-тэга), в hex.                                                                      |

### Формат файла v1 (legacy, auto-migrated)

Старый формат до миграции на argon2id. Поля `n, r, p` содержат параметры
scrypt (`N=32768, r=8, p=1`), `kdf="scrypt"`, соль 32 байта. При первой
успешной `LoadPrivateKey` файл переписывается в v2; рядом остаётся
резервная копия `<имя>.scrypt.bak`, которую можно удалить после
первой успешной проверки новой версии.

## Криптография (v2)

```
DK         = argon2id(passphrase, salt=16 rand, t=3, m=65536 KiB, p=4, dkLen=32)
ciphertext = AES-256-GCM(key=DK, nonce=12 rand, plaintext=raw_priv_key_32)
```

- **argon2id**: `golang.org/x/crypto/argon2`, RFC 9106. Параметры `t=3,
  m=64 MiB, p=4` соответствуют профилю «server» из OWASP Password
  Storage Cheat Sheet. Значения записываются в файл, так что при
  повышении дефолта в будущих версиях существующие файлы останутся
  читаемыми.
- **AES‑256‑GCM**: `crypto/aes` + `crypto/cipher.NewGCM`. Тэг
  аутентификации (16 байт) добавляется в конец `ciphertext`.
- **Источник случайности**: `crypto/rand.Reader` для соли (16 байт) и
  nonce (12 байт). Стойкость соответствует ОС.
- **Стирание**: после дешифрования и подписания программа обнуляет:
  - `passphrase` (`ZeroPassphrase`);
  - выведенный argon2id/scrypt-ключ (`zeroBytes`);
  - буфер плэйнтекста приватного ключа (`zeroBytes`);
  - материал ECDSA-ключа (`zeroPriv` обнуляет `D.Bits()`).

  Защита от утечек через swap/корки **не гарантируется** и зависит от
  ОС.

## Миграция v1 → v2

Автоматическая одноразовая процедура:

1. Вы запускаете любую команду, которая расшифровывает ключ: `hot
   send-trx`, `hot send-usdt`, `offline sign` или
   `wallet check`. `hot balance` ключ не расшифровывает (он читает
   адрес из открытых метаданных), поэтому миграцию **не запускает**.
2. monujo успешно дешифрует v1 файл scrypt-ключом и сверяет адрес.
3. **Только после успешной проверки** оригинальный `<имя>.json`
   переименовывается в `<имя>.scrypt.bak`, а его место занимает свежий
   v2/argon2id файл (атомарная запись через tmpfile + `rename`).
4. В stderr печатается строка `note: migrated wallet "..." from scrypt
   to argon2id; legacy backup saved as <имя>.scrypt.bak`.

Инварианты:

- Если миграция упала после шага 2, программа всё равно вернёт ключ
  вызывающей операции (она уже успешно дешифровала). Следующий запуск
  попытается мигрировать снова.
- При неверном пароле — никакой миграции и никакого бэкапа.
- Если `<имя>.scrypt.bak` уже существует (например, вы отменили
  операцию и запустили её повторно после редактирования файла),
  **второй бэкап не затирает первый** — он получит суффикс
  `<имя>.scrypt.bak.<unix-ms>`.
- `networks` из v1 переносятся в v2 без изменений.

Когда удалять `<имя>.scrypt.bak`: после того как вы подтвердили, что
любая подписывающая операция (`hot send-trx`, `hot send-usdt` или
`offline sign`) на новом v2 файле работает как ожидалось — именно она
доказывает корректность шифротекста. **Без сети** то же доказывает
`wallet check --addr ...`: она расшифровывает ключ и сверяет адрес,
не отправляя транзакций. `wallet list` показывает только открытые
метаданные и валидности зашифрованного содержимого не гарантирует.
До этого момента `.bak` — ваша страховка на случай, если внешние
условия (диск, ФС) повредили v2 файл в ходе записи.

Ручной откат: если по каким-то причинам нужна старая версия, удалите
`<имя>.json`, переименуйте `<имя>.scrypt.bak` обратно в `<имя>.json` и
запустите старую сборку monujo. Новая сборка не станет открывать
смешанные комбинации (`v2+scrypt` / `v1+argon2id`) — это защита от
случайного испорченного файла.

## Совместимость с non-ASCII паролями до NFKC-нормализации

Начиная с версии, в которой добавлена NFKC-нормализация (см.
«Соответствие стандартам» ниже), все passphrase приводятся к единой
форме перед KDF. Для ASCII-паролей это изменение **прозрачно**:
NFKC тождественна на ASCII, байты не меняются.

Если вы создали кошелёк на предыдущей сборке monujo с **non-ASCII**
паролем (кириллица, умлауты, лигатуры, full-width, emoji), возможно
одно из двух:

- Исходная байтовая форма уже совпадает с NFKC — всё работает без
  изменений (типичный случай на Linux/Windows, где терминал отдаёт
  уже скомпозированную форму).
- Исходная байтовая форма отличается от NFKC — например, macOS
  отдаёт NFD (`"café"` как `e`+`\u0301`), старая monujo передавала
  эти байты в argon2id «как есть». После обновления те же клавиши
  на той же машине превратятся в NFC-форму, и старый кошелёк
  **перестанет открываться**.

Вариантов решения два:

1. **Откатиться на старую сборку**, открыть кошелёк, получить
   приватный ключ (например, через скрипт, использующий старый
   `keystore.LoadPrivateKey`), и пересоздать через `wallet import` на
   новой сборке с любым паролем. Ключ и адрес останутся те же.
2. Если старой сборки нет — вручную «собрать» пароль из ожидаемых
   байтов и пропустить его через monujo через пайп без
   терминальной нормализации. Это хак на один раз; правильный путь
   — способ №1.

**ASCII-пароли этой проблемы не имеют.** Если вы не уверены,
использовали ли раньше non-ASCII пароль — после обновления проверьте
открытие кошелька: **`wallet check --addr ...`** (без сети) или
подписывающую операцию (`hot send-trx --from ...` с минимальной
суммой на тестовый адрес, или `offline sign`). `wallet list` и
`hot balance` пароля не запрашивают и эту проблему не диагностируют.

## Соответствие стандартам

- **NIST SP 800-132 — Password-Based Key Derivation.** Соль 128 бит из
  `crypto/rand`, уникальная на файл; параметры KDF записаны в файл.
  Требования к соли удовлетворены. SP 800-132 перечисляет PBKDF2 как
  одобренный KDF; monujo использует Argon2id как современную
  альтернативу, что **не** эквивалентно FIPS-approved списку (см.
  ниже).
- **OWASP Password Storage Cheat Sheet.** Параметры v2 (`t=3, m=64
  MiB, p=4, keyLen=32`) соответствуют профилю «server». Нижний
  приемлемый порог по cheat sheet — `t=2, m=19 MiB, p=1`; если в
  ваших условиях OWASP-дефолт по производительности избыточен,
  параметры можно понизить прямой правкой файла — они записаны в
  `argon2_*` полях.
- **NIST SP 800-63B §5.1.1.2 — Memorized Secrets.** monujo принимает
  произвольный UTF-8 passphrase, не форсирует ротацию и не
  ограничивает длину сверху. **Unicode NFKC-нормализация**
  применяется перед каждым вызовом KDF (Argon2id v2, scrypt v1,
  scrypt для offline HMAC). Это значит:
  - `"café"` (NFC, один кодпоинт `U+00E9`) и `"cafe\u0301"` (NFD,
    `e`+`\u0301`) дают один и тот же ключ;
  - лигатуры типа `"ﬁle"` (`U+FB01`+`le`) эквивалентны `"file"`
    (NFKC compatibility mapping);
  - full-width варианты `"ｐａｓｓ"` эквивалентны ASCII `"pass"`.

  Граница: NFKC **не** приравнивает визуально похожие, но кодпоинтно
  разные символы (кириллическое `а` ≠ латинскому `a`, греческая `ο`
  ≠ латинской `o`). Используйте одну раскладку клавиатуры при
  вводе пароля.
- **NIST SP 800-108 — KDF from PRF.** Регулирует вывод ключей из
  других ключей (например, HKDF), к паролевому KDF не относится и
  на monujo не распространяется.
- **FIPS 140-3 / ISO/IEC 19790 — Requirements for Cryptographic
  Modules.** monujo **не является сертифицированным криптомодулем**.
  Argon2id **не входит** в список FIPS-approved KDF (FIPS 140-3
  через SP 800-140C / SP 800-132 допускает для паролей только
  PBKDF2-HMAC-SHA2). Для сред, где обязателен FIPS 140-3 или ISO/IEC
  19790 compliance, monujo в текущем виде **не подходит** —
  используйте сертифицированный кошелёк либо ожидайте отдельного
  PBKDF2-режима (в этой версии отсутствует).

Итоговое позиционирование: retail/dev-утилита, следующая параметрам
OWASP и требованиям к соли SP 800-132, но **не** FIPS-совместимая и
**не** сертифицированная.

## Резервное копирование keystore

Файл `<имя>.json` самодостаточен: содержит адрес, соль, параметры KDF,
nonce и шифротекст. Парольная фраза **не хранится** в файле.
Бэкап = файл + пароль, и они должны лежать отдельно.

### Минимальная процедура

```bash
mkdir -p /path/to/backup
cp ~/.config/monujo/keystore/<имя>.json \
   /path/to/backup/<имя>.$(date +%F).json
chmod 600 /path/to/backup/<имя>.*.json
```

Проверить восстановление на стороннем носителе:

```bash
monujo --keystore-dir /path/to/backup wallet list
```

Адрес в выводе должен совпадать с исходным. Для более серьёзной
проверки — выполнить любую подписывающую операцию (`hot send-trx
--from <имя>` с минимальной суммой на тестовый адрес, или `offline
sign`) с этим `--keystore-dir`: только она докажет, что
зашифрованный материал действительно расшифровывается тем же
паролем (нулевые суммы для send-trx — норма, важна сама возможность
разблокировки).

### Утилита `tool vault` (рекомендованный путь)

`monujo tool vault pack` упаковывает **весь каталог keystore** в один
зашифрованный age-архив (scrypt passphrase recipient, RFC 9106-style);
`monujo tool vault unpack` делает обратное. Это тонкая обёртка над теми
же примитивами, что в age CLI — без exec во внешний бинарь, чистая Go-
зависимость `filippo.io/age`.

```bash
# Упаковать весь keystore в один файл (пароль запрашивается дважды).
monujo tool vault pack --out backup-$(date +%F).age

# Разложить обратно в целевой каталог (по умолчанию --keystore-dir).
monujo tool vault unpack --in backup-2026-04-21.age --out /restore/keystore

# Проверить, что адреса совпадают.
monujo --keystore-dir /restore/keystore wallet list
```

Что попадает в архив: только `*.json` и `*.scrypt.bak[.<unix-ms>]`.
Всё остальное (поддиректории, dotfiles, `.monujo-keystore-*.tmp`)
молча игнорируется. Имена внутри tar — «плоские», без префикса
каталога, чтобы распаковка была переносимой.

Флаги:

- `--armor` (pack) — ASCII armor (PEM-подобный текст), удобно для
  копирования через email/git/распечатку.
- `--overwrite` (pack) — разрешить перезапись уже существующего
  `--out`-файла. Замена атомарна: `monujo` пишет в соседний
  `.monujo-vault-*.tmp` и после успешного pack переименовывает его
  поверх старого архива; упавший pack не повреждает предыдущий
  бэкап. На TTY флаг ещё раз просит `[y/N]`.
- `--overwrite` (unpack) — разрешить перезапись существующих файлов
  в `--out`. По умолчанию unpack отказывается, если хотя бы один
  целевой файл уже есть (проверка до любых записей, частичной
  распаковки не бывает). На TTY флаг ещё раз просит `[y/N]`.
- `--dry-run` (unpack) — полная валидация (расшифровка, разбор tar,
  allowlist, проверка конфликтов) без единой записи на диск. Годится
  как «vault verify».

Ограничения:

- По умолчанию `--out` у `pack` должен не существовать (защита от
  затирания готового бэкапа); замена — только с явным `--overwrite`.
  Stdout допустим через `--out -`, там флаг `--overwrite` не нужен.
- Пароль vault — **отдельная сущность** от паролей keystore-файлов
  внутри. Теряете пароль vault — теряете архив; теряете пароль
  отдельного keystore — теряете этот кошелёк даже при целом архиве.
  Храните vault-пароль в том же уровне безопасности, что и keystore-
  пароли (менеджер / бумажный конверт), **не** на том же носителе,
  что архив.
- Age-совместимость: файл теоретически открывается обычным `age -d`
  (получите tar внутри), но это детали реализации, а не обещание
  стабильности формата; используйте `monujo tool vault unpack` для
  надёжного разбора с allowlist-проверками.

### Пароль храните отдельно

- Менеджер паролей (1Password, KeePass, Bitwarden) — основной
  рекомендованный вариант.
- Бумажный конверт в сейфе — для долговременных cold-бэкапов.
- **Никогда** не кладите пароль на тот же носитель, что и `.json`, и
  не сохраняйте в cloud sync без дополнительного слоя шифрования.

### Дополнительный слой шифрования (рекомендуется)

Поверх monujo-шифра можно обернуть файл ещё одним паролем. Пример с
`age`:

```bash
age -p -o wallet.json.age ~/.config/monujo/keystore/<имя>.json
age -d -o /path/to/restored/<имя>.json wallet.json.age
```

Либо GPG:

```bash
gpg -c --cipher-algo AES256 ~/.config/monujo/keystore/<имя>.json
gpg -d <имя>.json.gpg > /path/to/restored/<имя>.json
```

Такой бэкап безопаснее класть в облако / на email / на общие сетевые
диски: даже при утечке файла и метаданных monujo на нём остаётся
внешний пароль. Если нужно обернуть **весь каталог**, а не каждый
файл по отдельности, — используйте `monujo tool vault pack` (см.
выше): тот же примитив (age scrypt-mode), но одним архивом и с
allowlist-проверками при распаковке.

### Геораспределение

Минимум **две** копии:

- основной рабочий носитель (внешний SSD/USB, отдельный от машины с
  monujo);
- холодное хранилище (USB в сейфе / удалённое физическое
  местонахождение / облако с внешним age/GPG-паролем).

Для air-gap-сценария (см. `10-offline-commands.md`) бэкап keystore
**обязателен** и не должен пересекаться с online-машинами
(`build`/`broadcast`).

### Что НЕ является бэкапом

- `privHex` из `wallet create --export-private-key` без пароля — это
  «голый» приватный ключ, а не бэкап: без обёртки его утечка
  равносильна краже средств. Если вы его записали, храните как
  пароль (менеджер / бумага), удалите из `~/.bash_history` / буфера
  обмена.
- Скриншот с паролем или hex-ключом.
- Копия только пароля без `.json`.
- Копия только `.json` без пароля (но это шифр, а не отсутствие
  бэкапа: файл есть, доступа к ключу нет).

### Ротация и переезд

Переезд на новую машину: скопировать `.json`, ввести тот же пароль.
Если файл ещё v1 — на первой разблокировке сработает автомиграция,
после чего синхронизируйте бэкапы новой v2-версии. Файл v1 не нужен
после успешной миграции, но `<имя>.scrypt.bak` можно держать как
аварийную копию до первой успешной операции на v2.

### Восстановление доступа при утере пароля

**Невозможно.** Argon2id спроектирован так, что перебор пароля
вычислительно нецелесообразен при нормальной длине passphrase. Это
заявленный операционный риск (FIPS 140-3 / ISO/IEC 19790 и SP
800-63B явно его предусматривают): единственное средство —
надёжный бэкап самого **пароля**. monujo этой проблемы не решает и
не претендует решать.

## Метаданные `networks`

Поле `networks` — это «дневник» использований кошелька, помогающий
не перепутать mainnet с тестовой сетью.

### Когда заполняется

- При `wallet create --network <X>` и `wallet import --network <X>` —
  записывается `[X]`.
- После успешной отправки `hot send-trx`/`hot send-usdt` с
  `--network <X>` — если `X` отсутствует, добавляется
  (`EnsureNetworkRecorded`). Шифр не пересоздаётся, меняются
  только метаданные, файл переписывается атомарно.

### Когда проверяется

В трёх командах: `hot balance`, `hot send-trx`, `hot send-usdt`.
Логика: если массив `networks` **непустой** и
текущий `--network` в нём **отсутствует**, программа выводит
предупреждение в `stderr`:

```
Warning: wallet "myhot" was previously used on network(s): mainnet
The current operation uses network "shasta", which is not in that list.
This wallet has already been used in operations on the listed network(s).
```

Дальше:

- если задан `--force` — продолжает без вопросов;
- если STDIN — TTY — задаёт вопрос `Continue? [y/N]:`. Ответ
  `y`/`yes` (без учёта регистра) — продолжить, всё остальное —
  ошибка `aborted`;
- если STDIN не TTY — сразу ошибка `network mismatch: use --force to
  proceed without a terminal, or run interactively to confirm`.

### Нормализация

- Любой ввод приводится к нижнему регистру и к одному из канонических
  значений `mainnet`/`shasta`.
- Дубликаты схлопываются.
- Список сортируется (`slices.Sort`).
- Пустые/неизвестные значения отбрасываются.

Никакой явной команды для удаления записи из `networks` нет — массив
только дополняется. Если нужно «забыть» предыдущую сеть, отредактируйте
JSON вручную (поле `networks`).

## Как программа находит файл по имени или адресу

`hot balance`, `hot send-*`, `offline build`/`sign` и `wallet check`
обращаются к keystore по флагам **`--addr`** (субъект без `--to` в CLI)
или **`--from`/`--to`** (переводы и сборка unsigned). Команды
`wallet create`, `wallet import` и `wallet import-external` не позволяют
задать `--name`, который после нормализации выглядит как валидный Tron
base58-адрес — иначе это имя позже пересеклось бы с эвристикой «адрес
или имя» в тех же флагах.

Для записей **`import-external`** (`"external": true`) подстановка адреса
по имени работает там же, где для обычного кошелька достаточно поля
`address` в JSON; операции с **приватным ключом** (`LoadPrivateKey`,
`EnsureNetworkRecorded` для дописи сети после broadcast) для таких файлов
запрещены.

1. Если значение проходит Tron base58-валидацию — оно считается
   адресом.
   - Для **`--from`** в `hot send-*`, для **`--addr`** в
     `offline sign`/`wallet check` программа ищет соответствие через
     `keystore.ListWallets` (по полю `address` в plaintext-метаданных,
     без расшифровки); адрес обязан соответствовать локальному файлу,
     иначе команда завершится ошибкой (нужен приватный ключ).
   - Для **`--addr`** в `hot balance`, для **`--from`** в `offline build`
     и для **`--to`** везде несовпадение с локальным списком допустимо:
     `balance` может запросить баланс произвольного адреса,
     `offline build` на онлайн-машине не расшифровывает ключ,
     а `--to` — произвольный адрес получателя.
2. Если значение НЕ похоже на адрес, оно трактуется как имя:
   - Применяется `safeName` (превращение в безопасное имя файла).
   - Файл `<safeName>.json` открывается через
     `os.OpenRoot(keystoreDir)`.
   - Парсится JSON. Если `version` не в `{1, 2}` — ошибка
     `unsupported keystore version`.
   - Для `--to` из этого файла берётся только plaintext-поле
     `address`; никакой расшифровки приватного ключа не происходит.

То же самое делают `wallet *` (по `--name`). Это значит: если вы
изначально создали кошелёк с именем `My Cold`, файл получит имя
`My_Cold.json`, и обращаться к нему можно и как `--from "My Cold"`
(в `send-trx` / `offline build`), и как `--addr "My Cold"` (в
`hot balance` / `wallet check` / `offline sign`): строка нормализуется
к одному имени файла.

## Генератор парольных фраз

monujo включает встроенный генератор парольных фраз на `crypto/rand`
с равномерной выборкой без modulo-bias. Команда:

```bash
./build/monujo tool genpass [--words N] [--dict DICT] [--separator S]
                            [--capitalize] [--digits K]
                            [--allow-non-tty]
```

Те же параметры доступны в качестве опций `wallet create` и `wallet import`
через префикс `--generate-*`; при `--generate-passphrase` новая фраза
генерируется, печатается один раз в stderr и сразу используется как
пароль нового keystore-файла. Флаг `--generate-allow-non-tty` —
аналог `--allow-non-tty` для встроенного случая.

### Инварианты

- Источник случайности — **только** `crypto/rand.Reader`. Равномерная
  выборка через `rand.Int(rand.Reader, big.NewInt(N))`.
- Фраза NFKC-нормализована на выходе: байты, которые вы видите на
  экране, побитово совпадают с тем, что пойдёт в Argon2id.
- Вывод **только** в stderr и **только** один раз. В stdout фраза не
  пишется никогда (удобно в пайпах), в файл / clipboard / env не
  сохраняется.
- Если stderr не является терминалом, CLI отказывается печатать фразу
  без флага `--allow-non-tty` (или `--generate-allow-non-tty`) — это
  защита от случайного попадания пароля в логи CI.
- После печати буфер зачищается через `ZeroPassphrase`.

### Словари

| Флаг `--dict`    | Размер | Характеры      | Бит/слово | Когда выбирать                                            |
|------------------|--------|----------------|-----------|-----------------------------------------------------------|
| `english`        | 7776   | ASCII          | 12.92     | Дефолт, EFF Long Wordlist, канон.                         |
| `english-short`  | 1296   | ASCII          | 10.34     | Удобно диктовать голосом; короткие фразы.                 |
| `esperanto-x`    | 14851  | ASCII          | 13.86     | Эсперанто в x-system; безопасно на любой клавиатуре.      |
| `esperanto`      | 14851  | UTF-8 (ĉĝĥĵŝŭ) | 13.86     | Только если на всех машинах разблокировки настроен ввод.  |
| `russian`        | 15213  | UTF-8 (а-я,ёй) | 13.89     | Только при гарантированном Cyrillic IME везде.            |

Словари `esperanto` и `esperanto-x` — объединение частотного списка
Wiktionary/Wikipedia 2023 (15 000 лемм) и прежнего списка Tekstaro
(см. [internal/passphrase/wordlists/SOURCES.md](../internal/passphrase/wordlists/SOURCES.md)):
после `strings.ToLower` остаются только строчные буквы `a–z` и `ĉ ĝ ĥ ĵ ŝ ŭ`,
длина 3–12 рун; состав обоих флагов совпадает (x-system — механическая
замена диакритики).

Словарь `russian` — частотный список Ляшевской–Шарова (Национальный
корпус русского языка, 2009), 20 004 леммы в Wiktionary-зеркале; после
`strings.ToLower` остаются только строчные буквы `а-я ё й` длиной 3–10
рун — итого 15 213 слов. Написания без `ё` (`бобер`, `еще`) сохранены
как в первоисточнике; NFKC различает `ё/е` и `й/и`, см. ниже.

Минимум — 4 слова, дефолт — 7 слов. При ожидаемой энтропии меньше 80
бит CLI печатает предупреждение, но не прерывается.

### Предупреждения для non-ASCII словарей

При выборе `--dict esperanto` или `--dict russian` перед самой фразой
CLI печатает отдельный WARNING о требованиях к вводу:

- `esperanto` — предупреждение о необходимости ввода `ĉ ĝ ĥ ĵ ŝ ŭ` на
  каждой машине разблокировки; рекомендуется `esperanto-x` в
  сценариях без настроенной эсперанто-раскладки.
- `russian` — предупреждение про кириллический IME, различия `ё/е`
  и `й/и` после NFKC, а также про опасность латинских визуальных
  клонов (`a/а`, `o/о`, `e/е`).

### Что NFKC решает и что нет

NFKC-нормализация применяется к фразе перед тем, как она попадает в
Argon2id, поэтому разные способы ввода **одного и того же кодпоинта**
дают одинаковый ключ:

- `ĉ` (U+0109) ≡ `c`+U+0302 (декомпозиция).
- `й` (U+0439) ≡ `и`+U+0306.
- `ё` (U+0451) ≡ `е`+U+0308.
- Лигатуры `ﬁ` (U+FB01) → `fi`, full-width `ｐａｓｓ` → `pass` и т.д.

NFKC **не приравнивает**:

- `cx` и `ĉ` — это разные орфографические системы Эсперанто (x-system
  vs супер-signoj); выбирайте словарь один раз и не смешивайте.
- `ё` и `е` — разные кодпоинты, фразы `ещё` и `еще` дают **разные**
  ключи. То же верно для `й` и `и`.
- Визуальные клоны: кириллическое `а` (U+0430) и латинское `a`
  (U+0061) — разные буквы. Держите одну раскладку при вводе пароля.

Если фраза потеряна — она потеряна безвозвратно (см.
§«Восстановление доступа при утере пароля»).

### Примеры

```bash
# 7-слово EFF Long, разделитель — пробел (дефолт, ~90 бит).
./build/monujo tool genpass

# 8 слов + 2 цифры в конце, первые буквы в верхнем регистре.
./build/monujo tool genpass --words 8 --capitalize --digits 2

# Русский словарь, 7 слов, разделитель — дефис.
./build/monujo tool genpass --dict russian --separator -

# Сразу создать новый кошелёк со сгенерированным паролем.
./build/monujo wallet create --name cold --generate-passphrase \
    --generate-words 8 --generate-dict english
```

## Смена парольной фразы

Прямого CLI-механизма для смены пароля пока нет. Временный обход:
расшифровать ключ (через `LoadPrivateKey`-эквивалент невозможно из
shell — это API), либо при создании нового кошелька сохранить
`privHex` один раз, пересоздать через `wallet import` с новой фразой и
надёжно удалить старый файл. Отдельная команда `wallet rekey` —
запланированный follow-up.

## Что лежит **не** в keystore

- Парольная фраза. Программа никогда не сохраняет её на диск.
- Адреса третьих лиц (получатели). Программа не ведёт «адресной
  книги».
- Логи операций. monujo не пишет журналов, кроме обновления
  `networks`.
- Любые non‑Tron ключи (Solana/BEP — вне области видимости текущей
  версии).

## Совместимость с другими keystore

Формат monujo **не совместим** напрямую ни с keystore go‑ethereum,
ни с TronLink (собственный формат). Для миграции можно:

- из go‑ethereum: расшифровать там, получить hex‑ключ, импортировать
  через `wallet import --key-hex`;
- из TronLink/мнемоник: вывести приватный ключ нужного аккаунта
  (через расширение / CLI кошелька), импортировать.

`monujo` намеренно работает только с «голыми» приватными ключами
secp256k1 — без BIP39, без HD‑деривации.
